# 学会用三条件框架给 Agent 角色做体检

用户完成了第一课练习（docs/homework/character.md）：对作业 8 个角色逐一用「上下文污染 / 并行化 / 专门化」三条件判断存废。判断大体正确，且有两点需要修正，一次真实的理解需要被记录。

## 用户做对的（证据：docs/homework/character.md 的练习答案）
- 意图识别、调度、RAG 判为保留，理由基本正确
- 偏好 Agent 判为「可以用程序代替」——与教学建议一致
- **独立提出「联网查询可以跟 RAG、记忆统一成一个查询 Agent」**——这正是课程要训练的合并思维，且与参考答案吻合

## 需要修正的（misconception + 盲点）
1. **行程规划 Agent「可以用程序代替?」——错。** 它是核心价值产出者：LLM 结构化生成 + 政策依据引用 + 安排理由，且是基础项最低建议之一。程序无法替代，必须保留。已当场纠正。
2. **记忆查询「地位不清楚」——盲点。** 它和 RAG 是同一类：检索结果高体积、大部分与主问题无关 → 上下文污染场景，可与 RAG 合并成一个检索记忆 Agent。用户一旦套用三条件其实立刻能想通，属于没意识到可以套用。
3. 意图识别的理由（防污染）不精确：它最先执行，谈不上被污染；真正的理由是「单一严格的分类任务」= 提示词专门化。另需注意与调度划清边界。

## Implications
- 设计判断力已初步建立，下一课可以直接进入 LangGraph 实操（不用再补设计词汇）
- 行程规划 Agent 是后续实现的核心节点，教学时重点覆盖
- 用户在「检索/记忆/查询」这一类上的整合直觉强，后续讲 RAG 与记忆时可复用这个直觉
