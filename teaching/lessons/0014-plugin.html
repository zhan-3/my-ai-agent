Lesson 14 / 插件化架构

加一个 Agent 不用改主管：插件系统三机制

加分项 C 要求子 Agent 支持动态发现机制：自动扫描注册、懒加载、渐进式披露。这课实现一个完整插件系统，并演示最震撼的一幕——运行中热插拔新插件，主管自动认识新意图，一行代码不改。

插件系统三机制（对号入座）

加分项 C 要求机制代码
自动扫描注册目录扫描 + 元数据声明discover() glob plugins/*.py
渐进式披露（意图识别仅加载元数据）AST 静态解析，不执行模块read_metadata()
懒加载（未使用不加载）派发时才 exec_module + 缓存load_plugin()

插件公约：每个插件 = 元数据 + 一个函数

# plugins/stats.py —— 一个全新插件
print("  ⚠️ [stats] 模块已执行")        # ← 懒加载哨兵（exec 时才输出）

INTENT = "差旅统计"                      # ← 元数据：意图类别
DESCRIPTION = "统计历史出差目的地、次数"  # ← 元数据：给 LLM 的说明书

def run(query: str) -> str:             # ← 统一接口契约：query 进，文本出
    ...读记忆统计...

主管永远只认 INTENT + DESCRIPTION + run()，不关心插件内部——这就是「插件公约」。

渐进式披露：AST 只读元数据（不执行代码）

import ast
def read_metadata(path):
    tree = ast.parse(path.read_text())   # 只做语法树解析，不执行！
    for node in tree.body:
        if 是 "INTENT"/"DESCRIPTION" 赋值:
            meta[...] = ast.literal_eval(node.value)   # 安全求值字面量
    return meta

发现阶段如果 exec_module，就会连带执行插件的全部 import（如 policy 加载 chroma 索引）——那就违背「意图识别阶段仅加载元数据」了。AST 解析只读两个字面量，零执行。哨兵日志证实：第 1 幕发现 3 个插件时无任何「已执行」输出。

热插拔：动态发现的极致演示

演示第 3 幕：运行中往 plugins/ 写一个新插件 summary.py → 重新 discover() → 主管提示词的意图类别自动多一个「差旅总结」→ 提问命中新意图并正确路由。主管代码一行没改。

动态性的代价：静态类型变弱

原来的 Intent.intent: Literal[六类] 是编译期类型约束；插件化后类别运行时才知道 → 改用 str + 运行时校验（分类结果不在 manifest 就落「其他」）。这是插件化架构的固有权衡，真实插件系统都这么做——动态性换类型安全。
