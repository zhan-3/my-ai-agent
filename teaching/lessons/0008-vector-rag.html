向量检索：从关键词到语义

第七课的关键词检索能干活，但理解不了语义。这课用阿里 text-embedding-v3 + chromadb 升级，6/6 全对——包括关键词版必死的「语义题」。

关键差距：「临时要延长出差时间」里有个词是「时间」，环保文档写着「长时间不用电脑」——关键词检索被这个词骗走，向量检索用语义识别出真正相关的是 FAQ 里的行程变更流程。这就是 embedding 的价值。

向量检索三步

① embedding：文本 → 向量（阿里 text-embedding-v3，1024 维）
   文档块「…30个自然日内提交报销…」→ 向量 A
   问题「报销要多长时间内提交？」 → 向量 B
② 余弦相似度：cos(A, B) 高 = 语义相近（「时限」和「多长时间」语义近，向量近）
③ HNSW 索引：chromadb 用近似最近邻加速，百万级也快

核心直觉：语义相近的文本，向量方向接近。「时限」与「多长时间」词面不同，但在海量语料里常一起出现，所以 embedding 让它们向量接近——这就是「语义检索」的机制。

为什么用 chromadb（而不是 numpy 数组）

client = chromadb.PersistentClient(path="data/chroma")   # 磁盘持久化
col = client.get_or_create_collection("travel_docs", metadata={"hnsw:space": "cosine"})
col.upsert(ids=[...], embeddings=vecs, documents=[...], metadatas=[{"source": stem}])
col.query(query_embeddings=[qv], n_results=5)            # HNSW 近似最近邻
  • 持久化：向量落盘（data/chroma/），重启不重建——索引构建是一次性成本
  • 元数据：每块带 source（来源文档），以后可按来源过滤（"只查报销规定"）
  • 标准 API：增删改查齐全，真实产品直接迁移到 milvus/qdrant 等分布式向量库

诚实声明：向量检索的代价

① 依赖 API：阿里 text-embedding-v3 按量计费（¥0.0007/千 token，约 1 分钱 1 万条，新用户有免费额度）
② 冷启动：首次构建 386 块索引约 1-2 分钟（~39 次 API 调用）
③ 不可解释：命中后说不清「为什么相似」——关键词检索可以解释，向量不行
真实产品常做混合检索（关键词+向量，如 Elasticsearch hybrid / BGE-M3 同时支持两种）
