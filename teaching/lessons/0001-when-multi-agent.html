Lesson 1 / 多 Agent 设计

什么时候才需要多 Agent？

核心问题：你的作业清单上列了 8 个角色——它们真的都该存在吗？（基础项其实只要 5 个以上）

和你的使命的关系

你要学会的是设计多 Agent 系统。设计的第一件事不是"怎么搭"，而是判断要不要拆。这一课给你一把尺子——用三个条件去量你的差旅助手，每个角色能不能站住脚，一量便知。

先记住一个反直觉的事实

多 Agent 不是"更高级"，而是"更贵"。Anthropic 的实测显示：多 Agent 实现通常比单 Agent 方案多花 3–10 倍 token——上下文在多个 Agent 间复制、Agent 之间的协调消息、交接时的总结，都在烧钱。

血泪教训（原文引述）

Anthropic 见过团队花几个月搭出精巧的多 Agent 架构，最后发现改进单 Agent 的提示词就达到了同样效果。

所以官方建议的第一原则是："从最简单能用的方案开始，只有证据支持时才增加复杂度"。拆 Agent 必须有理由，而且必须是它解决不了的真实约束。

三个"值得拆"的条件

Anthropic 在多篇官方文章中反复确认：多 Agent 只在三种情况下稳定胜过单 Agent。

条件 ①

上下文污染

子任务产生大量高体积、但大部分与主任务无关的上下文，挤爆主上下文、拖垮推理。隔离出去，让它自己处理完再回报一个小结果。

条件 ②

并行化

任务可以并行，需要覆盖更大的搜索空间。注意：好处是更全面，不是更快——总时间通常反而更长。

条件 ③

专门化

工具超过约 20 个时选择退化；行为模式互相冲突（客服要耐心、审查要挑剔）；领域知识太多会压垮通用 Agent。

把三条件变成决策框架

  1. 存在真实约束吗？ 上下文受限、可并行、需要专门化——三条里至少一条成立，才谈得上拆。
  2. 按"上下文"拆，不是按"任务类型"拆。 原文原话："分组依据是任务需要什么上下文，而不是任务是什么类型。"（Anthropic）
  3. 有清晰的验证点吗？ 子 Agent 能在不搬走全部上下文的情况下交付可验证的结果。

术语对照：一个中心 Agent 负责拆任务、派人、汇总，就是 编排者-工人（orchestrator-workers）模式，也叫 主管（supervisor）模式——你的作业里，这就是"调度 Agent"。见术语表。

练一练

第一组：概念检查。每道题先凭记忆答，再看解析。

1. 多 Agent 系统平均比单 Agent 多花多少 token？

2. 下列哪项是「值得拆成多 Agent」的正当理由？

3. 工具太多会拖累工具选择，通常达到多少？

4. 拆 Agent 时，应主要按什么分组？

第二组：真实设计练习（本次的"战利品"）

作业全文给了 8 个角色（基础项要求至少 5 个，最低建议：意图识别 + 调度 + 要素提取 + 知识/RAG + 行程规划）。对每个角色写出两句话：
① 三个条件里，哪个为它站台？为什么？
② 如果站不住，你会怎么处理——合并？降级成工具？

参考答案（写完再展开）

调度 Orchestration —— 不用辩护：它就是编排者-工人模式里的"编排者"，是整个架构的骨架，不是可拆可不拆的部分。

记忆查询 / 知识 RAG —— 上下文污染站台：检索结果是典型的高体积、大部分与主问题无关的上下文，隔离出去最划算。这是全作业里最站得住的两个角色。

意图识别 Intention —— 系统提示专门化站台：分类需要单一、严格的指令模式。但它和调度有重叠风险——意图识别只回答"用户想要什么"，调度回答"流程怎么走"，边界要划清。

要素提取 Event Collection —— 上下文隔离勉强站台：输出是结构化小结果。但它很可能被调度 Agent 的一个工具替代，先做工具，出现污染再升格。

偏好 Preference —— 基本站不住：本质是一次读写偏好存储。先做成函数/工具，别急着独立成 Agent。

联网查询 Information Query —— 专门化（工具集）勉强站台：联网/天气/交通是一组清晰的工具。但它很可能只是"调度 Agent 的一堆工具"——先把查询做成工具，等工具超过约 20 个再拆出来独立。

行程规划 Itinerary Planning —— 专门化（领域知识 + 结构化输出）稳稳站台：它要生成结构化行程、引用差旅政策依据，是作业评分重点（结果可读性、设计合理性），而且是基础项最低建议之一——必须保留，别合并。

合并建议：基础项只要求 5 个以上。偏好 + 记忆查询 + 知识 RAG 三个"检索记忆类"可以先合并成一个 Agent（内部用工具路由），等真出现上下文污染再拆；联网查询先做工具。你的"最低配置"可以是：意图识别 + 调度 + 要素提取（可并入调度）+ 检索记忆 Agent + 行程规划。这个练习训练的是你的设计判断力——每个角色你都要能说出它存在的理由。

读完这一课，你带走了什么

  • 一把尺子：上下文污染 / 并行化 / 专门化，三个条件缺一不可谈拆分
  • 一条铁律：从最简单的方案开始，多 Agent 是 3–10 倍 token 的昂贵选择
  • 一个立刻能用的输出：对作业 8 个角色的"辩护词"或"合并提议"
