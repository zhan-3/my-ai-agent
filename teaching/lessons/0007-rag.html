Lesson 7 / 知识问答（基础项）

RAG：让系统「查资料」回答政策问题

用户问「报销要在多长时间内提交」，系统真的从政策文档里检索出「30 个自然日」并引用回答。这是作业基础项的核心能力。

和你的使命的关系

作业要求系统能回答企业差旅政策问题（报销、预订、标准、紧急情况）。知识库是 docs/documents/ 下的 8 份文档，共约 2.7 万字——塞不进上下文，也不能让模型瞎编，所以必须检索：只把相关片段给模型。这就是 RAG。

RAG 四步

① 索引构建（一次性）：8 份文档 → 分块(chunk) → 每块建词频索引
② 检索：问题 → 分词 → BM25 打分 → 相关 top-k 块
③ 增强：把命中的块拼进提示词（带来源标注）
④ 生成：LLM 只依据给定资料回答；资料没有就明说

真实产品用向量检索（embedding + 相似度）。你的中转站不支持 embedding（实测 404），所以本课用关键词检索（BM25）——教学上反而更清晰：检索机制看得见摸得着，且「索引与查询分离」的思路完全一致。

本课最宝贵的部分：4 轮调试，每轮一个真问题

第 1 轮：简单词频打分 → 短块吃亏，长文霸榜

「报销」在 04_faq 的大段落里出现 5-6 次，压过了 02 文档里真正写着「30 个自然日」的小块。升级 BM25（搜索引擎 Elasticsearch 的标准算法），三个升级：

  • 词频归一化：短块不吃亏
  • IDF：惩罚「报销」这种到处都有的词，突出「时限」这种独特词
  • 块长归一化：长块不占便宜

第 2 轮：分块策略——标题和内容要同块

「三、住宿标准」是 8 字的纯标题块，被块长归一化优待，压过了真正含「500 元/晚」的内容块 → 模型拿到空标题，说「内容为空」。修复：短块与下一块合并（标题+内容进同一块）。分块（chunking）直接决定检索质量，这是 RAG 工程的基本功。

第 3 轮：停用词 bug + 来源去重

STOPWORDS = set("了在是要…")      # ❌ 这是字符集合！
'什么'、'应该' 这些【词】根本没被过滤
STOPWORDS = set("…什么 应该 多长…".split())   # ✅ 按词定义

这个 bug 让「无论遇到什么紧急情况」的环保文档躺枪。另外加了来源去重（同一文档最多取 3 块），否则一个文档霸占全部名额。

第 4 轮：查询改写——问法与文档用词对不上

用户问「报销要在多长时间内提交」，文档写「30 个自然日内/时限」——关键词一个都对不上。解法是 Query Rewriting：用 LLM 把问句改写成检索关键词（含同义词）：

"报销要在多长时间内提交" → "发票 提交 时限 天数 期限"

改完后命中 02 文档「常规报销时限」块，答出 30 个自然日 + 一周内 + 逾期处理，完整准确。

诚实的质量声明：关键词检索的语义天花板

「临时需要延长出差时间」的问题因为含「时间」一词得分反超「30 个自然日」——关键词匹配不了语义。向量检索（embedding 相似度）+ 重排（rerank）能解决；你的中转站当前不支持，写作业文档时把这个「为什么先用关键词、升级路径是什么」讲清楚，是加分项。
