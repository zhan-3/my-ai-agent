Lesson 4 / 多 Agent 骨架

调度骨架：把「主管-工人」架构真正长出来

这一课，你的系统第一次成为「多 Agent」：一个主管（意图识别）指挥六个工人。

和你的使命的关系

作业要求「≥5 个 Agent」的多 Agent 架构。第一课你学会了判断为什么拆，第三课你做出了第一个真 LLM 节点（意图识别），这一课把它们串成一张会调度的图：主管读意图、按规则把人交给正确的工人——这就是作业里的 Orchestration 调度 Agent 落地的形态。

架构总览

                 ┌──────────── 行程规划 · itinerary ────┐
                 ├──────────── 偏好记录 · preference ───┤
用户输入 → 意图识别(主管) ─┼── 历史查询 · history ────┤→ 返回答案
    (LLM)      │            ├── 知识问答 · knowledge ───┤
                 └──────────── 联网查询 · web ────────┘

这就是主管-工人模式（Anthropic 分类里的 Orchestrator-Workers）：中心 Agent（意图识别）决定「交给谁」，六个工人各管一摊。注意：工人之间不互相调用、不知道彼此存在——协调完全靠主管 + 条件边，这就是「用代码协调」的含义。

① 主管节点：照旧是真 LLM

就是第三课那个 classify_intent，返回 intent 和 reason 写入 state。它是图里唯一「有大脑」的调度者。

② 六个工人：先做「桩」（stub）

def itinerary_stub(state):
    return {"answer": f"【行程规划·桩】我会为用户安排行程：{state['user_input']}（下节课做实）"}

桩节点是工程上的重要手法：工人先不接 LLM、只返回占位文字，让骨架先跑通——路由对不对、state 传没传对，全链路能立刻验证，代价只有几行代码。等骨架稳了，再逐个把工人「做实」。

③ 条件边：主管怎么「分单」

graph.add_conditional_edges(
    "classify_intent",                 # 主管节点
    lambda s: s["intent"],             # 路由函数：读 state 里的意图
    {
        "行程规划": "itinerary",        # 映射表：意图 → 工人节点
        "偏好记录": "preference",
        "历史查询": "history",
        "知识问答": "knowledge",
        "联网查询": "web",
        "其他": "other",
    },
)

第二课学的两种条件边写法在这里用上了映射字典版——因为意图是枚举值，一一对应最清晰。

映射表必须全覆盖

路由函数返回的每个可能值都得在映射表里有一条。漏了一个，LangGraph 会直接抛 KeyError——你的意图枚举和映射表是一份要同步维护的契约。以后加新意图，两个地方都要改。

练一练

1. 主管节点执行完返回什么？

3. 工人先做成「桩」的意义？

4. 映射表漏了某个意图值会怎样？
