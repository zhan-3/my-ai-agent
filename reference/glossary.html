多 Agent 系统 · 术语表

所有课程遵守这套词汇。增补新词时保持格式。

Agent（智能体） —— 一个 LLM 实例 + 工具 + 执行循环，能自主决定如何完成一个任务。区别于只"回答问题"的模型底座。

多 Agent 系统（Multi-Agent System） —— 多个 LLM 实例、各自独立的对话上下文，通过代码协调协作的架构。每个 Agent 负责任务的一个切片。来源：Anthropic, When and how to use them。

工作流（Workflow） —— LLM 和工具通过预先定义的代码路径编排的系统；流程固定，模型不控制路径。来源：Anthropic, Building Effective Agents。

主管（Supervisor） —— 一种多 Agent 模式：一个中心 Agent 决定"下一步交给谁"，其余 Agent 是被它调度的工人。等价于编排者-工人模式。

编排者-工人（Orchestrator-Workers） —— 中心 LLM 动态拆解任务、委派给工人 LLM、汇总结果的模式。适合"无法预判子任务"的复杂任务。来源：Anthropic, Building Effective Agents。

上下文污染（Context Pollution） —— 子任务产生大量高体积但大多与主任务无关的上下文，挤占主上下文、拖累推理质量。这是拆 Agent 的第一正当理由。

并行化（Parallelization） —— 多个 Agent 并行探索更大搜索空间。好处是全面性（thoroughness），不是速度——总 token 和时间通常更多。

专门化（Specialization） —— 不同任务配不同工具集 / 系统提示 / 领域知识。信号：工具超过约 20 个时选择退化；行为模式互相冲突时。

工具（Tool） —— Agent 可以调用的外部能力（函数调用、检索、查库）。工具是给"大脑"装上的"手脚"。

RAG（检索增强生成，Retrieval-Augmented Generation） —— 先从知识库检索相关内容，再交给模型生成的模式。作业里回答差旅政策问题用它。

状态（State） —— LangGraph 图里所有节点共享的数据结构（TypedDict）。每个 key 有独立的 reducer 决定如何应用更新。来源：LangGraph Graph API 文档。

节点（Node） —— 图里的一个普通 Python 函数：接收当前 state，做计算或副作用，返回部分状态更新。可以含 LLM，也可以只有纯代码。

边（Edge） —— 决定下一步执行哪个节点：add_edge 固定跳转，add_conditional_edges 用路由函数根据 state 决定去向。入口是虚拟节点 START，出口是 END。

归约器（Reducer） —— 定义某个 state key 的更新方式。默认 reducer 是「覆盖旧值」；消息列表用 add_messages 做追加。

ToolNode —— langgraph.prebuilt 提供的预制节点，负责执行模型发起的工具调用（含并行执行与错误处理）。标准 ReAct 场景官方推荐直接用 create_agent。我们第九课手写：条件边判断最后一条消息有 tool_calls → 进 ToolNode；否则结束。

工具调用（Tool Calling / Function Calling） —— LLM 在回答时自主决定调用外部函数的机制：模型输出结构化指令（用哪个工具、传什么参数），由宿主程序执行并把结果回填，形成 ReAct 循环。步骤：@tool 定义（docstring 是给 LLM 的说明书）→ bind_tools 挂载 → ToolNode 执行。需要模型支持（v4-flash tools+auto ✅ / 强制 tool_choice ❌）。

ReAct 循环 —— 模型思考 → 决定调用工具 → ToolNode 执行 → 结果回填 → 模型再思考，直到模型认为完成。是多 Agent 里每个子 Agent 内部的基本循环。

上下文（Context） —— 模型一次推理能看到的全部信息（对话历史、工具结果、系统提示）。多 Agent 设计的核心维度。

桩（Stub） —— 先返回占位结果的节点/函数，不接真逻辑，用来验证架构骨架（路由、state 传递）是否正确。骨架跑通后再逐个「做实」。工程上叫先桩后实。

要素提取（Event Collection） —— 从用户输入中结构化抽取任务要素（出发地、目的地、日期、天数、偏好等）。作业里是独立角色；本课程先做在行程规划 worker 内部（深模块：内聚优先，需要复用再拆）。

记忆（Memory） —— 系统的长期状态：用户偏好、历史行程等跨对话保留的数据。写入（偏好落库、行程归档）与读取（历史查询、生成时注入偏好）构成记忆闭环。真实产品用数据库/向量库 + user_id 隔离；本课程先用 JSON 文件演示概念。

结构漂移（Schema Drift） —— json_mode 等宽松结构化输出下，模型因上下文/发挥变化而改变输出结构（如字段变成嵌套对象），导致解析失败。对策：提示词钉死字段形状 + 上下文变更后重新验证。

分块（Chunking） —— RAG 中把长文档切成检索单元的步骤。分块策略直接决定检索质量：标题要和内容同块（纯标题短块会被 BM25 优待但无信息量）；块长需要平衡（太碎丢上下文，太大撑爆提示词）。

BM25 —— 经典关键词检索打分算法（Elasticsearch 默认）。三个升级 vs 简单词频：词频归一化（短块不吃亏）、IDF（惩罚常见词、突出独特词）、块长归一化（长块不占便宜）。

查询改写（Query Rewriting） —— RAG 工程手法：用 LLM 把用户问句改写成检索关键词（含同义词），弥合「问法」与「文档用词」的差异。如「多长时间内提交」→「时限 天数 期限」。向量检索下通常不再需要（embedding 天然懂语义）。

短期记忆（Short-term / Working Memory） —— 单个会话（thread）内的消息历史，随会话走。LangGraph 官方用 checkpointer 持久化、thread ID 隔离恢复；我们手写 JSON 版。关键：注入要截断最近 N 轮（hot path 权衡），别把完整长历史全塞上下文（超窗口/干扰/变慢变贵）。

长期记忆（Long-term Memory） —— 跨会话/跨线程共享，随时可召回：用户偏好、历史行程、常驻城市、出差习惯。官方用 store（namespace/key 组织 JSON + 语义搜索）；我们存 JSON 文件。管理方式分 Profile（单文档持续更新）和 Collection（窄记忆集合）。

追加/覆盖（Append vs Update） —— 记忆写入语义区分：「我喜欢住汉庭」是新增（追加）；「我现在常住上海」是更新（覆盖同类别旧条目）。用 is_update 标记，防止记忆无限膨胀和冲突。

Hot Path —— 在 agent 每次运行的推理路径上做记忆检索/写入。优点是实时、透明；代价是增加延迟、token 成本和复杂度。工程建议：检索克制（截断）、写入可选 background（异步、定时）分离主链路。

插件化（Plugin / Dynamic Discovery） —— 子 Agent 动态发现机制：目录扫描自动注册（discover）、渐进式披露（意图识别阶段用 AST 只读插件元数据、不执行代码）、懒加载（派发时才 exec_module + 缓存）、热插拔（运行中新增插件主管自动认识新意图，零代码改动）。插件公约：INTENT + DESCRIPTION + run(query)->str。代价：意图类别无法静态类型化，靠运行时校验兑底。

总装（Assembly / Integration） —— 多 Agent 系统开发后期把各 worker 模块组合成完整系统的过程。要点：①每个 worker 独立验证过；②接口契约统一（如统一「输入 state → 输出 answer」）；③总装文件只做「导入 + 挂图」，拓扑稳定、worker 可逐个替换。

向量检索（Vector Retrieval） —— embedding 把文本映射为向量，语义相近的文本向量方向接近，用余弦相似度检索。相比关键词检索能理解语义（「延长出差时间」≠「长时间不用电脑」），但依赖 embedding API/模型且命中不可解释。真实产品常做关键词+向量混合检索。

向量数据库（Vector Database） —— 专门存向量并提供相似度检索的系统。嵌入式代表 chromadb（磁盘持久化、HNSW 近似最近邻、元数据过滤）；分布式代表 milvus/qdrant。相比 numpy 数组：持久化、标准 API、可增删改。

embedding（嵌入） —— 把文本/词映射成稠密向量的过程。模型在海量语料中学习「语义相近的文本向量接近」。本课程用阿里 text-embedding-v3（1024 维）。
